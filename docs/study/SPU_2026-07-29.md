# SPU — study against the hardware documentation

**Date**: 2026-07-29. **Method**: `DOCS/soundprocessingunitspu.md` read as the authority, then
DuckStation (`duckstation_ref/src/core/spu.cpp`, `src/util/core_audio_stream.cpp`) and PCSX-Redux
(`pcsx-redux/src/spu/`) read as second opinions, then our `src/spu/*` compared against both. Every
claim below carries a citation; anything not verified is labelled as a hypothesis.

This is a findings document, not a work order. Nothing here has been changed yet.

---

## What is already right

Worth recording so it does not get re-investigated:

- **Sample tick**: 768 CPU cycles per sample, taken from the emulated cycle counter. Matches the
  documented 33.8688 MHz = 768 × 44100 (`DOCS/soundprocessingunitspu.md:1058-1060`) and DuckStation's
  `SYSCLK_TICKS_PER_SPU_TICK = 0x300` (`spu.cpp:69`).
- **Flush-before-mutate**: we catch up on *every* SPU register read and write (`src/spu/spu.c:147`,
  `:289`). DuckStation is selective about which registers force a sync (`spu.cpp:873-1161`); ours is
  stricter, which is safe.
- **Event granularity**: our 64-sample batch is finer than DuckStation's, whose tick event runs at one
  sample only when SPU IRQs are enabled and otherwise as coarse as the whole audio ring — up to 35328
  samples with default settings (`spu.cpp:2548-2565`).
- **Key-on/key-off**: latched, applied key-off first, ENDX cleared on key-on, both latches cleared
  (`src/spu/spu.c:47-96`). Same ordering as DuckStation (`spu.cpp:2510-2531`).
- **ADSR rate tables**: our numerator/denominator model is arithmetically equivalent to DuckStation's
  shift/counter model across the whole 0-127 rate range (verified numerically, not by eye).
- **Noise**: neither reference implements the LFSR the documentation describes
  (`DOCS/soundprocessingunitspu.md:533-541`); both use Dr. Hell's reconstruction, and ours matches
  them bit for bit (`src/spu/spu_mixing.c:26-47`).
- **Reverb formula and address units**: the rewrite landed today is a faithful transcription, and
  `register × 4` halfwords is the correct reading of "addresses divided by 8".
- **Reverb resampling shortcut**: skipping the documented 39-tap FIR (`:907-913`) in favour of
  averaging the input pair and holding the output costs aliasing and high-frequency response in the
  wet signal **only**. Measured against the coefficients: unity gain either way, no change to level,
  decay time or reverb length. It cannot explain a shortened jingle.

## Findings, most serious first

### 1. `mBASE` is truncated to 14 bits — the reverb writes into the sample region

`spu->reverb_base = value & 0x3FFF` (`src/spu/spu.c:336`). mBASE is a full 16-bit address-divided-by-8
covering all 512 KB of SPU RAM; DuckStation stores `(value << 2) & 0x3FFFF` (`spu.cpp:991`).

Concretely, for the "Room" preset in the documentation (work area 0x26C0, so mBASE =
(0x80000 − 0x26C0) / 8 = **0xFB28**) we keep 0x3B28 and start the work area at byte **0x1D940**
instead of **0x7D940**. ADPCM sample data starts at 0x1000 (`DOCS/soundprocessingunitspu.md:37`), so
the reverb's delay line runs straight through it.

### 2. SPUCNT bit 7 gates the wrong half of the reverb

The documentation is explicit: bit 7 "disables writes to reverb buffer, but reads from reverb buffer
do still occur" (`:826-835`), confirmed by the bus-timing table (`:1113-1123`). DuckStation gates only
the four `ReverbWrite` calls (`spu.cpp:2282-2306`, `:2330-2334`).

We do the opposite: `reverb_process` writes unconditionally (`src/spu/spu_mixing.c:139-177`) and the
flag only decides whether the result is mixed into the output (`:296`).

**Together, 1 and 2 mean the reverb corrupts voice sample data even while a game has reverb switched
off.** A corrupted ADPCM header byte with bit 0 set is a Loop-End flag, which our decoder turns into a
stop (`src/spu/spu_voice.c:174-181`), silencing that voice on the next sample (`:225-231`).

**Hypothesis, not yet verified**: this is the mechanism behind the boot jingle ending after ~8 seconds
where hardware takes 10-15, and behind part of the residual crackle. Cheap check before fixing
anything: log mBASE on write and compare `reverb_base * 4` against the region the game DMAs its
samples into.

### 3. Capture buffers are not in SPU RAM

The four 1 KB capture regions at SPU RAM 0x000/0x400/0x800/0xC00 hold CD-L, CD-R, voice 1 and voice 3,
and games read them back for lip-sync (`:33-38`, `:739-747`, `:758-765`). We write them into a private
array instead (`include/spu.h:262`, `src/spu/spu_mixing.c:53-62`), so a game reading that memory sees
whatever was there before. Three further defects in the same code: the position advances by 2 (a byte
step) but indexes a halfword array, so only even slots are written and the wrap period is doubled; the
CD samples captured are post-volume where the documentation says pre-volume; and there is no IRQ check
on capture writes.

### 4. Volume sweeps read the direction from the wrong bit

Sweep direction is bit 13 (`:370`; DuckStation `sweep_direction_decrease` at bit 13, `spu.cpp:155`).
We read bit 7 (`src/spu/spu_voice.c:284`, `:304`), which the documentation lists as unused — so every
sweep runs in the wrong direction. Phase-invert (bit 12) is not implemented at all.

### 5. Writing a sweep-mode volume register destroys the current level

"Sweep starts at the current volume" (`:379-383`). We assign `value & 0x7FFF` — the sweep
configuration bits reinterpreted as a level — into the current volume (`src/spu/spu.c:239`, `:246`,
and the same for main volume at `:309`, `:317`). DuckStation leaves `current_level` untouched and only
resets the envelope (`spu.cpp:1830-1841`).

### 6. Main volume sweeps never advance

`main_vol_left_cur` / `main_vol_right_cur` change only when the register is written
(`src/spu/spu.c:305-320`). DuckStation ticks both every frame (`spu.cpp:2499-2500`).

### 7. `VxPitch` is masked at write time, so the documented maximum stops the voice

We store `value & 0x3FFF` (`src/spu/spu.c:251-252`). A write of 0x4000 — documented as the fastest
step (`:167`, `:209-213`) — becomes 0 and the voice stops advancing; values above that truncate
instead of clamping, and register read-back no longer returns what was written. DuckStation keeps the
raw value and clamps only after pitch modulation (`spu.cpp:1220`, `:2105`).

### 8. Mute and SPU-disable silence CD audio

SPUCNT bit 14 is "Don't care for CD Audio" (`:553-554`). We apply mute at the final main-volume stage
(`src/spu/spu_mixing.c:302-306`), after CD audio and reverb have joined the mix. DuckStation zeroes
voices and the reverb input *before* CD audio is added (`spu.cpp:2443-2449`).

### 9. SPU IRQs cannot fire from inactive voices, and the address check is off

Voices that are off return immediately without reading RAM (`src/spu/spu_voice.c:201-204`), but the
documentation says inactive voices keep reading and keep triggering IRQs (`:726-737`); DuckStation
keeps sampling whenever `SPUCNT.irq9_enable` (`spu.cpp:2046`). Our check also tests
`curr_addr + 16` (`src/spu/spu_voice.c:161-164`) where DuckStation tests `addr` and `addr + 8`
(`spu.cpp:2019`).

### 10. SPU transfers are instantaneous

DMA4 and manual writes move the whole block at once (`src/core/bus.c:978-1002`,
`src/spu/spu_dma.c:9-65`), so SPUSTAT's busy and DMA-request bits carry no timing. DuckStation models
a 32-halfword FIFO and a transfer event at 16 ticks per halfword (`spu.cpp:77`, `:1374-1512`).
`TRANSFER_TICKS_PER_HALFWORD` is already declared in our header (`include/spu.h:27`) and used nowhere.

### 11. Repeat-address writes always disable the ADPCM loop-start flag

Any write to voice register 0x0E sets `ignore_loop` unconditionally (`src/spu/spu.c:275-280`).
DuckStation sets it only when the voice is off or past its first block, with a comment naming the
games that depend on the distinction (`spu.cpp:1256-1279`).

### 12. Smaller deviations

- End+Mute is honoured even for voices in noise mode (`src/spu/spu_voice.c:174-181`); DuckStation skips
  the force-off there (`spu.cpp:2127-2138`).
- Pitch modulation's factor is not clamped to ±0x8000, so it can reach 3.0× instead of the documented
  1.99× (`src/spu/spu_voice.c:214-220` against `:191-193`).
- Interpolation uses the PEOPS 1024-entry table rather than the hardware's 0x200-entry Gaussian table
  (`:187-201`; DuckStation `spu.cpp:1937-2013`). Same resolution, different normalisation.
- The exponential-increase ADSR adjustment is always ÷4; DuckStation splits it three ways by rate
  (`spu.cpp:1786-1798`). The "all rate bits set never steps" case (`:441-442`) is absent.
- Dead state to remove: `reverb_ds_buf`, `reverb_us_buf`, `reverb_resample_pos`, `last_reverb_input`,
  `last_reverb_output` (`include/spu.h:265-270`), plus `GAUSS_TABLE_SIZE` and
  `TRANSFER_TICKS_PER_HALFWORD`.

## Host output when the emulator is below 100% of real time

This is our open problem, so it is worth recording exactly what the two references do.

**DuckStation — time stretch, driven by buffer fullness.** `AudioStretchMode::TimeStretch` is the
default (`core_audio_stream.h:39`) with a 50 ms target buffer and a ring 16× that size
(`core_audio_stream.cpp:444-448`). After every 64-frame chunk it computes `tempo = buffered_frames /
dynamic_target`, smooths it over a 50-sample moving average, damps it with `sqrt` below 2.0, and feeds
it to SoundTouch; a hysteresis band leaves the stretcher inactive while tempo stays within ±4% and
re-engages past ±20% (`core_audio_stream.cpp:765-897`). **Tempo changes, pitch does not**, and nothing
is dropped or duplicated in the steady state — their own UI labels the alternatives "Resampling (Pitch
Shift)" and "Time Stretch (Tempo Change, Best Sound)" (`core_audio_stream.cpp:230-234`). Only the
emergency underrun path improvises: with *some* frames available it spreads them over the request with
a nearest-neighbour resampler rather than inserting silence, and memsets only when the ring is
completely empty (`core_audio_stream.cpp:328-359`).

**PCSX-Redux — pace the emulator from the device.** Its SPU thread blocks when the 2048-frame ring is
full (`support/circular.h:53-60`, `spu/spu.cc:796-806`), and the counter code blocks the CPU itself
until the audio callback has consumed a target number of frames (`core/psxcounters.cc:158-176`). The
callback zero-fills on underrun (`spu/miniaudio.cc:190-196`).

**Ours** is Redux's shape without Redux's producer-side block: the host loop waits while the ring is
above target (`src/main.c:422-425`), which can only ever slow the emulator down, and the callback pads
with silence (`src/spu/spu_mixing.c:483-487`). When the emulator is slower than real time nothing
compensates — which is precisely the crackle being heard.

So the two available answers are: make the core fast enough, or adopt something in the shape of
DuckStation's tempo feedback. They are not exclusive.

## On the shortened boot jingle

Ranked candidates from inside the SPU:

1. Reverb corrupting sample RAM (findings 1 + 2) — strong hypothesis, cheap to test.
2. Dropped output samples, which literally remove audio time (`spu->dropped_samples`,
   `src/spu/spu_mixing.c:408`) — already instrumented, should be read before theorising.
3. Sweep direction (finding 4): a voice that should fade in fades out to zero instead.
4. `spu_catch_up`'s one-second resync discarding an interval (`src/spu/spu_mixing.c:443-447`) — only
   reachable after a debugger pause; `system_init` does initialise the timestamp.

Ruled out: the reverb resampling approximation, the ADSR rate tables, and the pitch counter scaling
(`sinc = pitch << 4`, 0x1000 = 1.0×), all verified correct.

Arithmetically, 8 seconds of wall clock at 85-95% of real time means the guest produced only about 7.2
emulated seconds of audio, so the compression is in **emulated** time. If none of the above accounts
for it, the cause is outside the SPU — the guest walking its sequence in too few emulated cycles,
which points at CPU cycle accounting rather than at anything in `src/spu/`.
