# CDROM async behaviour and CD-XA audio — study against the hardware documentation

**Date**: 2026-07-29. **Method**: `DOCS/cdromdrive.md`, `DOCS/cdromformat.md`,
`DOCS/cdrominternalinfoonpsxcdromcontroller.md` and `DOCS/cdromfileformats.md` read as the authority,
then DuckStation (`duckstation_ref/src/core/cdrom.cpp`) and PCSX-Redux
(`pcsx-redux/src/core/cdrom.cc`, `src/core/decode_xa.cc`) as second opinions, then our
`src/cdrom/*` compared against both. Findings were checked against a live instrumented boot of
`Ace Combat 2 (Europe)` (45 s wall clock, 1272 VBlanks ≈ 25.4 emulated seconds).

Clock: 33 868 800 Hz. Cycles → ms = cycles / 33868.8.

---

## What is already right

- **Sector period constants**: 451 584 cycles at 1x, 225 792 at 2x (`include/cdrom.h:25-26`). The
  documentation derives exactly these: `SystemClock × 0x930 / 4 / 44100`
  (`DOCS/cdromdrive.md:1917-1920`).
- **XA samples per sector** — the count fixed on 2026-07-28 is correct.
  `samples_per_chunk = num_blocks × 28` (`src/cdrom/cdrom_audio.c:228-244`) gives 4032 / 2016 / 2016 /
  1008 frames for 4-bit mono / 4-bit stereo / 8-bit mono / 8-bit stereo, matching DuckStation's
  `XA_ADPCM_SAMPLES_PER_SECTOR_4BIT = 4032` and `_8BIT = 2016` (`cdrom.cpp:58-59`). At 2x with the
  standard 1/8 interleave, one 37800/stereo sector every 53.33 ms produces 2352 output frames = exactly
  53.33 ms of playback at 44100 Hz. The arithmetic closes.
- **The 37800 Hz resampler is the documented algorithm**: 29 taps, 7 phase tables, six-step counter,
  `>>15` per tap, ±0x8000 clamp (`src/cdrom/cdrom_audio.c:122-197` against
  `DOCS/cdromformat.md:879-925`). The tables match DuckStation byte for byte. *(Note: there is no
  "39-tap FIR" anywhere in the CD documentation — that filter belongs to the SPU's reverb resampler.
  The CD side uses this 29-tap zigzag.)*
- **ADPCM sample expansion** matches the documentation for both depths, including the `+32` rounding
  term in the filter (`cdrom_audio.c:113`) which DuckStation omits.
- **Muted XA is still decoded** before the early return (`cdrom_audio.c:243`), so filter state stays
  correct across a mute — same as DuckStation.
- **Request Register (BFRD) semantics**: disarm resets the read position, arm does not
  (`src/cdrom/cdrom.c:316-327`), matching DuckStation `cdrom.cpp:1250-1259`. This was fixed earlier and
  still holds.
- **Data start offset** `raw + 24` (12 sync + 4 header + 8 subheader) and subheader fields at
  `raw[16..19]` are correct.

## Findings, most serious first

### 1. The XA coding-info bit masks are wrong

```c
bool xa_stereo = (coding & 0x01) != 0;   /* correct */
bool xa_8bit   = (coding & 0x04) != 0;   /* wrong — 0x04 is the sample rate */
bool xa_18900  = (coding & 0x08) != 0;   /* wrong — 0x08 is reserved, always 0 */
```
`src/cdrom/cdrom_commands.c:634-636`.

The documented layout, given identically in two places (`DOCS/cdromformat.md:664-671` for the
subheader and `DOCS/cdromdrive.md:265-278` for the CI register):

| bits | meaning |
|---|---|
| 0-1 | mono / stereo |
| **2** | **sample rate — 0 = 37800 Hz, 1 = 18900 Hz** |
| 3 | reserved |
| **4** | **bits per sample — 0 = 4-bit, 1 = 8-bit** |
| 6 | emphasis |

Confirmed by DuckStation's bitfields (`cdrom.cpp:271-274`) and Redux's macros
(`decode_xa.cc:277-280`).

Consequences: an 18900 Hz sector (coding 0x04/0x05) is decoded as 8-bit 37800 → noise; a genuine 8-bit
sector (0x10/0x11) is decoded as 4-bit → noise; 18900 Hz is never detected, so `resample_xa_18900` is
unreachable. Only the common 37800/4-bit case works — which is why this survived until now.

### 2. The 18900 Hz resampler has the wrong ratio

`src/cdrom/cdrom_audio.c:199-217` reuses the 37800 six-step structure: consume one input per step,
emit 7 outputs every 6 inputs = **7/6**. For 18900 → 44100 the ratio is **7/3**. DuckStation counts
`sixstep += 3` and consumes an input only when it reaches 7 (`cdrom.cpp:3792-3810`), and uses a
different 25-tap table from Mednafen for this rate. Once finding 1 is fixed, 18900 Hz XA would play an
octave low at half speed.

### 3. A queued second response is silently discarded

```c
void cdrom_schedule_second_response_event(Cdrom *cdrom, uint32_t cycles) {
    if (cdrom->second_event_pending) return;
```
`src/cdrom/cdrom.c:77-82`, and the same guard on the command event at `:65-70`.

The new command's INT2 then fires at the *old* command's deadline, or not at all. **Measured on a live
boot: 12 `Init` commands produced 3 second responses; one burst of ten consecutive Inits produced
exactly one.** DuckStation cancels and re-schedules instead (`cdrom.cpp:2726-2731`).

The command path also *drops* a command that arrives while one is pending (`cdrom.c:274-277`).
Hardware defers it until the pending interrupt is acknowledged (`DOCS/cdromdrive.md:1802-1818`);
DuckStation implements the deferral with a parameter-count heuristic (`cdrom.cpp:1832-1877`). No drop
occurred in the measured boot, so this one is latent.

### 4. The drive stops while an interrupt is pending, and overrun cannot happen

`cdrom_drive_event_tick` returns without rescheduling whenever `interrupt_flag != 0`
(`src/cdrom/cdrom.c:95-107`); the drive is restarted from the acknowledge path, a full sector period
measured from the ack (`:338-346`).

Hardware does the opposite: the drive keeps delivering 75 (or 150) sectors per second and "the software
must be fast enough" (`DOCS/cdromdrive.md:747-754`); if the CPU is late, sectors are silently skipped
and the next INT1 jumps to the newest one (`:1927-1987`). There are no overrun flags. DuckStation
reproduces this — the drive event re-arms itself unconditionally (`cdrom.cpp:3381-3507`), a separate
async-interrupt event publishes INT1 and only then advances the readable buffer (`cdrom.cpp:1499-1501`),
missed sectors are counted, and a still-buffered missed sector is re-delivered after the DMA finishes
(`cdrom.cpp:4093-4104`).

Our effects:
- The INT1 period becomes *ISR latency + sector time*, so data reads are always **slower** than 75/150 Hz.
- Overrun is structurally impossible; no game can ever observe a dropped sector.
- The 8-slot buffer ring is 1-deep in practice, because `current_read_buffer` is advanced when a sector
  *lands* (`cdrom_commands.c:669`) rather than when its INT1 is delivered. Hardware locks a sector once
  BFRD has been issued (`DOCS/cdromdrive.md:771-773`).
- Any acknowledge re-arms the drive — including an unrelated INT3, e.g. a GetlocL issued during a read,
  which pushes the next sector out by another full period.

The XA path is the exception and is correct: it self-schedules at the sector period because it
produces no INT1 (`cdrom_commands.c:651-653`).

### 5. Filtered-out XA sectors are delivered to the CPU as data

`file_match` gates entry into the XA branch (`cdrom_commands.c:637-641`); on a mismatch control falls
through to the data branch at `:655` and fires an INT1. The documented algorithm rejects data delivery
for audio+realtime sectors whenever the filter is enabled (`DOCS/cdromdrive.md:583-605`, specifically
`:597`), and DuckStation returns unconditionally after the XA attempt (`cdrom.cpp:3523-3532`). In an
interleaved multi-channel stream this fires spurious INT1s carrying ADPCM bytes.

Related, same area: we never check that the sector is Mode 2 before reading `raw[18]/raw[19]` as
submode/coding (DuckStation gates on `sector_mode == 2`, `cdrom.cpp:3523`), and we do not track the
"current XA file/channel" the way DuckStation does to reject stray sectors even with filtering off
(`cdrom.cpp:3851-3878`).

|---|---|---|---|---|

| Pause, 1x | 1 000 000 (`cdrom.h:56`) | **2 168 860** (`DOCS/cdromdrive.md:1888`) | ≥2 000 000 | **swapped with 2x** |
| Pause, 2x | 2 000 000 (`cdrom.h:57`) | **1 097 107** (`:1889`) | ≥1 000 000 | **swapped** |
| Stop | 6 773 760, speed-independent (`cdrom.h:52`) | 13 863 626 (1x) / 25 845 878 (2x) (`:1891-1892`) | 13M / 25M | 2-3.8× short |

| Reset (0x1C) | INT3 **+ INT2** (`cdrom_commands.c:452-460`) | INT3 only, no second INT (`:539-548`) | ack only | **sends an interrupt hardware never sends** |

Also missing: DuckStation's minimum gap between interrupts — it delays an INT1 by 500 cycles if fewer
than 1000 have passed since the last interrupt was cleared, because Ogre Battle, Crime Crackers and
Lego Racers poll GetlocL/GetlocP during XA playback and would otherwise read an INT1 response while
expecting an INT3 (`cdrom.cpp:80-81`, `:1459-1481`).

One status detail: our Pause INT3 samples the status byte after setting `DRIVE_PAUSING`
(`cdrom_commands.c:241-244`), so it reports bit 5 clear where hardware still reports it set
(`DOCS/cdromdrive.md:576-581`). Stop happens to be correct.

### 7. The CD volume matrix is mis-decoded and then never used

Four 8-bit attenuators route CD-L and CD-R into the SPU's left and right inputs, 0x80 = normal
(`DOCS/cdromdrive.md:227-255`). In our decode:

- `1F801801`/index 3 is **ATV2 (R→R)** and is silently discarded (`src/cdrom/cdrom.c:287`).
- `1F801803`/index 3 is **ADPCTL**, not a volume register, but we store its data byte into `vol_rr_t`
  and commit it (`cdrom.c:355-365`). A routine `ADPCTL = 0x20` write therefore sets the right-to-right
  gain to 25 %.
- `ADPMUTE` (ADPCTL bit 0) is not implemented.
- None of `vol_ll/lr/rl/rr` is read anywhere in the tree — the CD audio path bypasses the matrix
  entirely, and `cdrom_get_audio_frame` (`cdrom.c:387-389`) is dead code because the SPU pops the FIFO
  directly.

### 8. ADPCM filter state is stored unclamped

`src/cdrom/cdrom_audio.c:112-117` writes the raw prediction into `xa_prev` and clamps only the output.
The documentation clamps first and feeds the clamped value back (`DOCS/cdromformat.md:836-837`), as
does DuckStation (`cdrom.cpp:3655-3661`). On loud material the IIR state can run away.

Nearby: we accept filter index 4 (`cdrom_audio.c:80`), but XA has only filters 0-3 — index 4 belongs to
SPU-ADPCM (`DOCS/cdromformat.md:846-847`). DuckStation zero-fills indices 4-15.

### 9. Smaller deviations

- **CDDA is not decimated at 2x**: we always push 588 frames per sector (`cdrom_audio.c:253-259`) while
  the drive runs at 150 Hz, a 2:1 overproduction. DuckStation halves it (`cdrom.cpp:4025-4027`).
- **Report mode fires on every CDDA sector** (75/s, `cdrom_commands.c:743-757`). Hardware reports only
  when the absolute sector is 00/10/20/…/70 (`DOCS/cdromdrive.md:1071-1082`), about 10/s, and includes
  peak bytes we never compute.
- **Auto-pause tracks the previous track in a function-local `static`** (`cdrom_commands.c:723`), so it
  survives disc changes and resets.
- **INT delivery ignores the interrupt mask**: `interconnect_trigger_cdrom_irq` is called
  unconditionally (`cdrom.c:39,45,54,682,713,732,756`); `cdrom_has_pending_interrupt` masks correctly
  but nothing calls it on that path. Latent, because the BIOS keeps HINTMSK = 0x1F.
- **Audio FIFO policy differs by three orders of magnitude**: we allow ~213 ms of standing latency and
  drop the oldest frame (`include/cdrom_audio.h:7-14`); DuckStation keeps the FIFO under 10 frames and
  drops the whole incoming sector (`cdrom.cpp:70`, `:3885-3897`). Its failure mode preserves waveform
  continuity; ours introduces a discontinuity per dropped frame.
- `sample_buf` is still sized for the old 8× bug — 32 256 samples where 4032 suffice
  (`cdrom_audio.c:232`).

## The compressed boot is not a CDROM problem

Measured on the instrumented run:

- **The CD is idle during the logo and jingle.** Between the last licence-sector access and the first
  `Init` of the boot-file sequence there are 115 VBlanks (2.3 s at 50 Hz) and 4 CDROM log lines out of
  4256. No CD constant, long or short, can compress that window.
- **Our read path is slower than hardware, not faster** (finding 4), and a typical file access costs
  ≈ 4.1 M cycles ≈ 121 ms, with a Pause 1.8× longer than hardware and a short-seek floor 10-100×
  longer than DuckStation's.
- **Total CD-attributable shortfall over the whole boot ≈ 1.8 s**: 0.6 s of missing speed change plus
  ~1.2 s of Init second responses collapsed by finding 3.
- **The BIOS prints `VSync: timeout` 1032 times in 25 emulated seconds** (~40/s), starting *before* the
  first CD command. `VSync()` returning early instead of blocking for a field makes every BIOS-side
  frame-counted animation run faster than 50 Hz — which is exactly the reported symptom.

**Next lead for the boot pacing is the VBlank / root-counter / event-delivery path, not the CDROM.**

## Concrete work items

Ordered by ratio of impact to effort.

1. Fix the coding-info masks (finding 1) — three lines, unblocks every non-37800/4-bit XA stream.
2. Fix the 18900 Hz resample ratio (finding 2) — needed the moment finding 1 lands.
3. Make `cdrom_schedule_second_response_event` cancel and re-schedule instead of dropping (finding 3).
4. Charge the Setmode speed change, and swap the Pause 1x/2x constants (finding 6) — small, and worth
   ≈ 0.6 s of emulated time by itself.
5. Stop delivering filter-rejected XA sectors as data, and gate the XA attempt on Mode 2 (finding 5).
6. Clamp the ADPCM filter state before feeding it back (finding 8).
7. Decide the drive-pacing model (finding 4). This is the structural one: re-arm the drive event
   unconditionally, move `current_read_buffer` to INT1 delivery, and accept that sectors can be missed.
   It changes behaviour broadly, so it wants its own session and a regression pass.
8. Wire the CD volume matrix, or delete the fields and say so (finding 7).
9. The rest of finding 9 as cleanup.
